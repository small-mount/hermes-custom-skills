# Frame-level evidence extraction

实测来源：BV1Z6e46bEki（2026-10-07，24 个模型 × 8 维雷达图/评级抽取）；BV1jAdYBdETH（2026-10-07，口播数字与烧录字幕冲突、owner/repo 与 UI 数值的 OCR 复核）。适用场景：从视频画面中提取结构化数据（榜单、评级、评分、表格）。

## 滚动/动画数字
- 卡片数据普遍带入场动画（数字滚动、淡入、柱状生长），**初次抽帧读到的常是动画中间值**。
- 定位"稳定帧"：动画结束后约 0.5–1s。判定方法：连抽 2–3 帧对比，读数一致才采信。
- 实测教训：#1 首读 SS+，复核 3 连帧后实为 SSS（全满面板），首读为动画中间值。

## 多帧连拍复核
- 对存疑/高价值数据项抽 3 帧（间隔 1–1.5s），同一模型的多帧放同一行拼网格（2 模型 × 3 帧 = 2×3 网格），一次读取并明确要求"对比 3 帧给出稳定值"。
- 复核优先级：① 与其他帧有矛盾的 ② 排名最高的 ③ 结构特殊（双列）的。
- 置信度写入报告：单次读数标"单次"，复核过的标"复核"；同一维度两次读数不一致时标 ± 区间而非硬取一值。

## 双列（旧值 → 新值）
- 部分卡片同屏显示"上期→本期"两列（带箭头/降升标记）；读取时必须先确认列数与动画状态，报告中取**本期**值并注明"双列，取本期"。
- 把双列读成单列（取错列）是此类数据最常见的错误来源。

## 拼图批量读取流程
1. ffmpeg 抽帧：`-ss <T> -i video.mp4 -frames:v 1 -q:v 2`。
2. 裁剪数据区：`crop=850:720:0:0`（左上区域；不同版面先侦察再定 crop）。
3. 拼网格：`hstack`/`vstack`，2×3 或 2×2；同一模型相邻时刻放同一行，便于对比。
4. `scale=2048:-2` 后交给视觉模型；一个网格 ≤6 帧，超过易漏读。
5. 视觉模型对 2048 宽拼图读取良好；要求"逐帧对比 + 输出稳定值 + 注明双列"。

## 时间戳规划
- 先按视频结构估算每个条目窗口（实测约 5–9s/卡），窗口内抽"中段+末段"两帧最稳。
- 相邻条目边界帧可能处于切换过程（模糊/混合）；抽帧避开边界 ±0.5s，必要时用前后条目名确认身份。
- 卡片名与数据不同步切换；以"数据区完整显示"的帧为准。

## 静帧 vs 音轨
- 音频转录里的数字读数与静帧画面可能不一致（口播/口误/BGM 干扰）；以画面证据为准，差异两方都记录。

## 标识符与屏幕条目复核（BV1jAdYBdETH 实测）
- 屏幕上的 owner/repo、用户名等标识：≥2 张不同高分辨率帧的裁剪读取一致后才采信。整帧 OCR 实测出错：forrestchg / forrestchan（实为 forrestchang）、小艾助手（实为小龙虾）。
- GitHub 界面按按钮语义逐项对读（Star / Fork / Watch 各归各位）：曾把 Fork 3.7k 读成 star 数。
- 烧录字幕与音频转录冲突（数字、英文术语）：字幕按频道自述文本证据与 ASR 读数并列记录，不静默取一。

## 总结页与概念架构图
- 工具清单优先用总结页的两张稳定帧加音频复核；避免在叠化过渡帧读清单。BV153pf6JEeS 实测中，整片模型把“网页”猜成 RustDesk/开源桌面，把 UU 远程误加为 1Password；1305/1307 秒稳定帧与音频才确认四组工具。
- 视觉模型会凭模糊水印编造作者名，视频身份以平台元数据为准；不要让水印 OCR 覆盖已核实的作者信息。
- 概念图里没有端口、IP、YAML、服务端实现名称时明确记“未提供”；官方文档中的默认端口只能作为外部补充，不能写成视频给出的配置。
